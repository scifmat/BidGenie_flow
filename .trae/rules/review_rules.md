# 内容审查规则

本规则文档用于指导 reviewer-agent 审查技术方案正文，必须严格遵循。

## 一、内容完整性审查规则

### 1.1 content_plan 覆盖要求
- 正文必须覆盖 content_plan 中的**所有要点**
- 要点覆盖率 ≥ 80% 为合格

### 1.2 要点覆盖判断方法
- **关键词匹配**：检查正文是否包含 content_plan 中要点的核心关键词
- **语义理解**：关键词匹配不充分时，通过语义理解判断要点是否被覆盖
- **宽松匹配**：允许使用同义词、近义词替代原关键词

### 1.3 问题分级标准

| 判定条件 | 问题级别 |
|----------|----------|
| 缺失要点 ≥ 2 个 | 严重问题（serious） |
| 缺失要点 = 1 个 | 一般问题（general） |
| 轻微遗漏（覆盖率 60%-80%） | 建议性问题（suggestion） |
| 覆盖率 ≥ 80% | 合格 |

### 1.4 content_plan 解析规则
- content_plan 格式：`1. 要点1；2. 要点2；3. 要点3`
- 按分号（；或 ;）分割为独立要点
- 去除序号前缀（如 `1. `、`2. `）
- 每个要点作为一个独立的检查项

## 二、评分点响应审查规则

### 2.1 评分标准响应要求
- 正文必须充分响应 07_Evaluation_Criteria.md 中的**所有评分点**
- 每个评分点必须有对应的论述内容

### 2.2 评分点响应判断方法
- **关键词匹配**：检查正文是否包含评分点的核心关键词
- **语义理解**：通过语义理解判断是否充分响应评分点要求
- **评分权重考量**：高权重评分点需要更详细的响应内容

### 2.3 问题分级标准

| 判定条件 | 问题级别 |
|----------|----------|
| 未响应评分点 ≥ 1 个 | 严重问题（serious） |
| 响应不充分（内容简略、未展开论述） | 一般问题（general） |
| 完全响应（内容详细、论证充分） | 合格 |

### 2.4 评分点提取规则
- 从 07_Evaluation_Criteria.md 中提取评分项名称、评分标准、分值
- 识别评分项的技术要求部分（非商务、非资质部分）
- 按评分项分值权重判断响应充分性：
  - 高分值评分项（≥5分）：需要详细论述
  - 中分值评分项（2-4分）：需要适当论述
  - 低分值评分项（<2分）：需要基本响应

## 三、技术与语言规范审查规则

### 3.1 逻辑漏洞检查

**检查内容**：
- **逻辑矛盾**：同一章节内或跨章节之间的内容矛盾
- **逻辑跳跃**：缺乏必要的论证步骤，直接得出结论
- **不合理假设**：基于未说明或不合理的假设进行论述

**问题分级**：逻辑漏洞为**严重问题（serious）**

### 3.2 内容重复检查

**检查内容**：
- **章节内重复**：同一章节内的重复表述
- **跨章节重复**：不同章节之间的内容重复

**问题分级**：
- 内容重复率 > 20%：**一般问题（general）**
- 内容重复率 ≤ 20%：合格

**重复率估算方法**：
- 提取正文中的关键段落（≥50字的连续文本）
- 对比不同章节的段落相似度
- 估算整体重复率

### 3.3 语言风格检查

**检查内容**：
- **术语一致性**：同一术语在全文中保持一致
- **语言专业性**：使用专业术语，避免口语化表达
- **格式规范性**：遵循附件7的正文撰写规范

**问题分级**：语言风格不一致为**建议性问题（suggestion）**

### 3.4 技术准确性检查

**检查内容**：
- **技术参数准确性**：技术参数和数据的准确性
- **技术方案可行性**：技术方案的可行性和合理性
- **标准规范引用**：正确引用相关标准和规范

**问题分级**：
- 技术参数错误：**严重问题（serious）**
- 技术方案不可行：**严重问题（serious）**
- 标准规范引用错误：**一般问题（general）**

## 四、问题分级规则

### 4.1 严重问题定义
**影响方案完整性或评分结果的问题**：
- 缺失要点 ≥ 2 个
- 未响应评分点 ≥ 1 个
- 逻辑漏洞
- 技术参数错误
- 技术方案不可行

**处理策略**：必须优化，审查完成后统一进入阶段七

### 4.2 一般问题定义
**影响方案质量但不影响核心评分的问题**：
- 缺失要点 = 1 个
- 响应不充分
- 内容重复率 > 20%
- 标准规范引用错误
- 实际字数少于计划字数偏差 > 15%（脚本审查，与阶段五一致，只下限不限上限）
- Mermaid 语法错误（脚本审查）
- 图表数量不匹配（脚本审查）
- 标题格式错误（脚本审查）

**处理策略**：建议优化，审查完成后统一进入阶段七

### 4.3 建议性问题定义
**提升方案质量的改进建议**：
- 轻微遗漏（覆盖率 60%-80%）
- 语言风格不一致
- 表述不够专业
- 图题格式错误（脚本审查）
- 段落格式不规范（脚本审查）

**处理策略**：视情况优化，审查完成后统一进入阶段七

## 五、审查分流规则

### 5.1 审查通过判定

| 判定条件 | 处理方式 | 是否需要人工介入 |
|----------|----------|------------------|
| 严重问题数量 ≥ 1 | 审查完成，进入阶段七进行优化 | 否（优化阶段完成后人工审查） |
| 严重问题数量 = 0，一般问题数量 > 0 | 审查完成，进入阶段七进行优化 | 否（优化阶段完成后人工审查） |
| 仅建议性问题 | 审查完成，进入阶段七进行优化 | 否（优化阶段完成后人工审查） |
| 无任何问题 | 审查完成，进入阶段七进行优化 | 否（优化阶段完成后人工审查） |

### 5.2 流程说明

**阶段六 → 阶段七（优化）→ 人工审查 + 优化循环（最多3次）→ 阶段八（合并导出）**

阶段六仅作 AI 自动审查，**所有审查完成后统一进入阶段七进行优化**，优化完成后再启动人工审查和优化循环。

### 5.3 字数偏差处理策略（与阶段五一致，只下限不限上限）
- 实际字数少于计划字数偏差 > 15%：一般问题，需补充内容
- 实际字数超过计划字数：仅记录，不限制（鼓励充分论述，不判定为问题）

## 六、优化建议编写规则

### 6.1 优化建议要求
- **具体可行**：建议必须具体，能够直接指导优化工作
- **针对性强**：建议必须针对具体问题，不泛泛而谈
- **参考依据**：建议可以引用招标文件或技术标准作为依据

### 6.2 优化建议格式
```markdown
【优化建议】：XXX
【参考依据】：XXX（如适用）
【实施步骤】：XXX（如适用）
```

### 6.3 优化建议示例

**示例1（内容完整性）**：
```markdown
【优化建议】：建议在 1_1_1 节点正文中补充"地膜使用现状分析"的相关内容，包括当前地膜使用量、回收率、残留情况等数据
【参考依据】：招标文件第3.2节"采购内容"中明确要求分析地膜使用现状
【实施步骤】：1. 查阅相关行业数据；2. 结合竹山县实际情况分析；3. 在正文相应位置补充分析内容
```

**示例2（评分点响应）**：
```markdown
【优化建议】：建议在 1_2_1 节点正文中增加对"服务流程总体设计"评分点的响应内容，详细描述服务流程的设计思路和关键环节
【参考依据】：07_Evaluation_Criteria.md 中"技术服务方案"评分项明确要求"每项内容完整、可行"
【实施步骤】：1. 梳理服务流程关键环节；2. 描述流程设计思路；3. 说明流程的可行性和完整性
```

## 七、审查结果输出规范

### 7.1 JSON 输出格式
```json
{
    "review_type": "content_completeness",
    "review_time": "2026-07-XX XX:XX:XX",
    "review_results": [
        {
            "level": "serious",
            "description": "问题详细描述",
            "node_id": "影响的节点ID",
            "node_title": "影响的节点标题",
            "dimension": "content_completeness",
            "suggestion": "具体的优化建议"
        }
    ]
}
```

### 7.2 字段说明

| 字段 | 类型 | 说明 | 取值 |
|------|------|------|------|
| review_type | string | 审查任务类型 | content_completeness / scoring_response / technical_language |
| review_time | string | 审查完成时间 | YYYY-MM-DD HH:MM:SS |
| review_results | array | 审查结果列表 | - |
| level | string | 问题级别 | serious / general / suggestion |
| description | string | 问题描述 | 详细的问题描述 |
| node_id | string | 影响节点ID | 对应 outline.json 中的 node_id |
| node_title | string | 影响节点标题 | 对应 outline.json 中的 title |
| dimension | string | 审查维度 | 与 review_type 一致 |
| suggestion | string | 优化建议 | 具体可行的优化建议 |

### 7.3 问题描述规范
- 问题描述清晰明确，指明具体问题位置和内容
- 问题描述使用简洁的语言，避免冗长
- 问题描述包含足够的上下文信息，便于理解
